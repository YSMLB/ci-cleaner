# ci-cleaner

Утилита для Linux освобождает место на VPS с CI-раннерами. За один запуск она проверяет свободное место на разделе с кэшем указанного Buildx-билдера. По умолчанию работает в dry-run.

| Условие | Действие |
|---|---|
| Свободно не меньше порога | Проверяет доступность билдера через `buildx inspect` и завершает проход |
| Свободно меньше порога, dry-run | Показывает сводку `buildx du` и аргументы запланированной очистки |
| Свободно меньше порога, включён `--apply` | Выполняет `buildx prune` с фильтром по времени последнего использования кэша и повторно измеряет свободное место |

## Сборка и первый запуск

На VPS нужны Linux, Docker CLI с плагином Buildx и доступ к Docker от имени пользователя, запускающего утилиту. Для таймера нужен systemd. Из корня репозитория с Go 1.21 или новее выполните:

```sh
go test ./...
go build -o ci-cleaner .
sudo install -m 0755 ci-cleaner /usr/local/bin/ci-cleaner
sudo docker buildx ls
sudo docker info --format '{{.DockerRootDir}}'
```

Выберите локальный выделенный билдер, который используют CI-сборки. Сервис запускается от root, поэтому билдер должен быть виден в выводе **sudo docker buildx ls**. Укажите каталог на разделе, где физически хранится его кэш. Для стандартной установки с локальным Docker volume это обычно раздел DockerRootDir. Удалённый билдер хранит кэш на другом хосте.

```sh
ci-cleaner --help
sudo ci-cleaner --docker-dir /var/lib/docker --builder ci-builder
# Реальная очистка при нехватке места
sudo ci-cleaner --docker-dir /var/lib/docker --builder ci-builder --apply
```

| Флаг | Значение |
|---|---|
| `--docker-dir` | Обязательный существующий каталог на разделе билдера |
| `--builder` | Обязательное имя CI-билдера |
| `--min-free-gib` | Порог в ГиБ, по умолчанию 25. Значение 0 отключает порог |
| `--min-free-after-gib` | Минимальный остаток после очистки в ГиБ. Берётся из `CI_CLEANER_MIN_FREE_AFTER_GIB`, если флаг не задан. Значение 0 отключает проверку |
| `--min-free-after-inodes` | Минимальный остаток inode после очистки. Берётся из `CI_CLEANER_MIN_FREE_AFTER_INODES`, если флаг не задан. Значение 0 отключает проверку |
| `--min-cache-age` | Минимальный возраст с последнего использования записи кэша, по умолчанию 30m |
| `--apply` | Разрешить удаление подходящего кэша |

Используйте один каталог для всех запусков на VPS. Утилита удерживает блокировку на нём до конца прохода. Параллельный запуск с тем же каталогом завершится с результатом `already_running`. Общий таймаут для команд Docker — две минуты.

## Таймер на VPS

Установите файлы из репозитория:

```sh
sudo install -m 0644 deploy/systemd/ci-cleaner.service deploy/systemd/ci-cleaner.timer /etc/systemd/system/
sudoedit /etc/default/ci-cleaner
```

Пример содержимого для вашего VPS:

```ini
DOCKER_DIR=/var/lib/docker
BUILDER=default
MIN_FREE_GIB=0
MIN_CACHE_AGE=30m
APPLY_FLAG=
CI_CLEANER_MIN_FREE_AFTER_GIB=15
CI_CLEANER_MIN_FREE_AFTER_INODES=10000
```

Сначала проверьте один проход и журнал, затем включите таймер:

```sh
sudo systemctl daemon-reload
sudo systemctl start ci-cleaner.service
sudo journalctl -u ci-cleaner.service -n 50 --no-pager
sudo systemctl enable --now ci-cleaner.timer
systemctl list-timers ci-cleaner.timer
```

Первый запуск запланирован через две минуты после загрузки, последующие — через десять минут после завершения прохода. Чтобы включить очистку, задайте `APPLY_FLAG=--apply` в файле настроек. Сервис прочитает его при следующем запуске. Для возврата к dry-run очистите значение. Чтобы отключить расписание, выполните `sudo systemctl disable --now ci-cleaner.timer`.

В журнале `free_before_kib`, `free_after_kib` и `free_delta_kib` указаны в КиБ. Если после успешного `prune` запас места или inode ниже заданного минимума, проход пишет `result=low_space_after_prune` и завершается с кодом 1. Dry-run показывает план и сохраняет код 0. Коды выхода также различают ошибку выполнения (1) и ошибку аргументов (2).

Для очистки по таймеру при любом объёме свободного места задайте `MIN_FREE_GIB=0` и `APPLY_FLAG=--apply` в `/etc/default/ci-cleaner`. Фильтр `MIN_CACHE_AGE` применяется при каждом запуске.

## Защита раннеров от переполнения

### Обновление работающего VPS

Сохраните текущие бинарник и конфигурацию перед заменой. Если `systemctl cat ci-cleaner.service` показывает drop-in с `flock`, сохраните его. Новый бинарник читает параметры запаса из того же `EnvironmentFile`. На уже установленном сервере достаточно заменить бинарник и обновить `/etc/default/ci-cleaner`, сохранив действующие значения `DOCKER_DIR`, `BUILDER` и `MIN_CACHE_AGE`.

```sh
# Из каталога с новым бинарником ci-cleaner. Выполнить от root.
backup="/root/ci-cleaner-backup-$(date +%Y%m%d-%H%M%S)"
install -d -m 0700 "$backup" &&
cp -a /usr/local/bin/ci-cleaner /etc/default/ci-cleaner "$backup/" &&
install -m 0755 ci-cleaner /usr/local/bin/ci-cleaner.next &&
mv -f /usr/local/bin/ci-cleaner.next /usr/local/bin/ci-cleaner
editor /etc/default/ci-cleaner
```

Добавьте `CI_CLEANER_MIN_FREE_AFTER_GIB` и `CI_CLEANER_MIN_FREE_AFTER_INODES` из примера выше. Значения 15 ГиБ и 10 000 inode подходят для первого испытания. Для рабочего порога измерьте пиковое потребление места и inode у самых крупных заданий на каждом разделе, учтите одновременно работающие процессы и оставьте запас под журналы и временные файлы. Проверьте статус и журнал после следующего запуска таймера:

```sh
systemctl list-timers --all ci-cleaner.timer
journalctl -u ci-cleaner.service -n 50 --no-pager
```

Подключите алерт существующего мониторинга на остаток байтов и inode на каждом разделе CI и на ошибку `ci-cleaner.service`. Сигнал по самому разделу помогает и тогда, когда запуск cleaner пропущен из-за занятой блокировки. Вводите изменения в рабочую эксплуатацию после доставки тестового алерта.

### Проверка задания и сериализация сборок

```sh
install -m 0755 deploy/runner/ci-build-guard deploy/runner/ci-runner-preflight /usr/local/bin/
install -m 0644 deploy/runner/ci-build-guard.conf /etc/tmpfiles.d/
systemd-tmpfiles --create /etc/tmpfiles.d/ci-build-guard.conf
```

Для проверки каждого задания добавьте в существующий `.env` каждого self-hosted runner следующие параметры. Укажите его фактический рабочий каталог и место хранения Docker. Если у раннера уже настроен стартовый хук, вызовите `ci-runner-preflight` из него. Перезапускайте службы раннеров по одной после завершения активных заданий.

```ini
ACTIONS_RUNNER_HOOK_JOB_STARTED=/usr/local/bin/ci-runner-preflight
CI_RUNNER_DOCKER_DIR=/var/lib/docker
CI_RUNNER_WORK_DIR=/path/to/runner/_work
CI_RUNNER_MIN_FREE_GIB=15
CI_RUNNER_MIN_FREE_INODES=10000
```

Хук завершит задание до запуска его шагов, если один из разделов уже ниже минимума. Чтобы две тяжёлые команды на одном VPS проверяли место по очереди, в шагах CI оборачивайте **всю команду, которая занимает место**, в `ci-build-guard`. Например, внутри шага Docker build:

```sh
ci-build-guard --min-free-gib 25 --min-free-inodes 10000 \
  /var/lib/docker "$GITHUB_WORKSPACE" -- docker build -t app:test .
```

Подберите порог для сборки по измеренному пику. Обёртка ждёт общий lock до 120 секунд, проверяет указанные разделы и удерживает блокировку до завершения команды. Если места не хватает или истёк таймаут, команда не запускается. Используйте один файл блокировки для всех раннеров на VPS. Проверяйте, что пути существуют и доступны пользователю службы. Если отдельный раздел используется для containerd, кэша или временных файлов, добавьте его путь в проверку. Для фонового Compose запустите под обёрткой весь сценарий с ожиданием и teardown, чтобы нагрузка укладывалась в период блокировки.

### Условия приёмки на VPS

- От имени пользователя службы выполните `ci-cleaner check-space` для всех фактических путей. Запросите заведомо недостижимый минимум и убедитесь, что хук или обёртка возвращает ошибку до запуска сборки. Проверьте доставку алерта без заполнения рабочего диска.
- Запустите две тестовые команды через обёртку. Вторая проверяет диск после завершения первой. Проверьте, что все тяжёлые задания используют обёртку, включая вызовы сборки из скриптов.
- Чтобы одна сборка не заполнила системный раздел даже при превышении расчётного расхода, изолируйте хранилище Docker, containerd и рабочие данные CI отдельными файловыми системами или квотами. Систему, сервисы и журналы раннеров держите с отдельным запасом. Монтирование и квоты зависят от VPS. На одноразовом разделе проверьте исчерпание лимита во время тестовой сборки и убедитесь, что ОС и раннер остаются доступны.

Для отката бинарника и конфигурации восстановите обе копии из каталога `backup`. Если откатываете версию без `check-space`, предварительно снимите хук и вызовы обёртки, чтобы они не блокировали задания.
